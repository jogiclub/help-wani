# 상담 위젯 운영 기능 — 인사말 / 팔로업 알림 / 운영 시간

상담 대화(`/console/chat`) > 설정 드로어에 세 기능을 더하는 기획입니다.
상담 위젯의 기본 구조는 `docs/widget-plan.md` 를 따르고, 여기서는 **바뀌거나 늘어나는 것만** 적습니다.

> **2026-10-22 진행 상황**: 인사말(2장)과 연락처 카드·팔로업 메일(3장)을 구현했습니다. 운영 시간(4장)은 같은 시기에
> `docs/chat-operation-plan.md` 가 조직당 운영 시간 1개로 먼저 구현했으므로 그것을 그대로 씁니다. 처음 안과 달라진 점은 10장에 있습니다.

| 기능 | 한 줄 요약 |
|---|---|
| 인사말 | 위젯을 열었을 때 첫 문구. 언어별로 따로 쓰고, `{{이름}}` 같은 변수와 바로가기 버튼을 넣는다 |
| 팔로업 알림 | 고객 연락처(이메일/휴대폰/이름)를 받아 두고, 고객이 떠난 뒤 상담원이 답하면 알린다 |
| 운영 시간 | 요일별 운영 시간과 휴일을 정하고, 시간 밖에서는 부재 안내를 보여준다. 운영 설정을 여러 개 둘 수 있다 |

---

## 0. 지금 상태와 차이

| 항목 | 지금 | 바뀌는 것 |
|---|---|---|
| 첫 화면 | 고정 문구(`widget.title`, `widget.subtitle`) | 조직이 쓴 인사말, 언어별 |
| 위젯 언어 | 조직 설정 하나(ko/en/ja) | 브라우저 언어를 따르는 선택 사항 추가 (**3.2 규칙 변경 필요, 9장 1번**) |
| 이름/이메일 | 위젯 위쪽 입력칸, 항상 노출, 선택 | 설정에 따라 대화 안의 **연락처 카드**로 받는다. 휴대폰 추가 |
| 접속 상태 | 상담원 `last_seen_at` 60초 이내면 온라인 | 운영 시간과 상담원 접속을 함께 본다 |
| 상담원 답장 알림 | 없음(조직에 보내는 오프라인 메일만 있음) | 고객에게 이메일 알림(1단계), 문자/알림톡(나중) |
| 예약 작업 | 없음 | **만들지 않는다.** 알림은 상담원이 보낼 때 바로 판단한다(3-4) |

## 1. 설정 화면 구성

지금 드로어는 한 화면에 모든 항목이 들어 있습니다. 항목이 세 배로 늘어나므로 **드로어 안에 탭을 둡니다.**
새 메뉴는 만들지 않습니다(CLAUDE.md 3.6, 상담 위젯 설정은 상담 대화의 설정 드로어).

```
상담 위젯 설정                                         [닫기]
[ 설치·모양 ][ 인사말 ][ 팔로업 ][ 운영 시간 ]
-----------------------------------------------------------
 (탭 내용)
-----------------------------------------------------------
                                          [취소] [저장]
```

- 탭마다 저장 API 를 따로 둡니다. 탭 하나를 저장할 때 다른 탭 값을 함께 덮어쓰지 않게 하려는 것입니다.
- 운영 시간 탭은 목록과 편집 모달로 구성합니다(2-3).
- 드로어를 넓게 씁니다(`drawer-panel` 에 넓은 변형 클래스 추가). 운영 시간 표가 좁으면 읽기 어렵습니다.
- 바꾼 설정은 모두 `audit_logs` 에 남깁니다(3.7).

## 2. 인사말

### 2-1. 고객이 보는 화면

```
+------------------------------+
| 데모 조직          ● 운영 중 |
|------------------------------|
|  [로고]                      |
|  홍길동님 안녕하세요!        |   <- {{이름}} 이 있으면 채우고, 없으면 기본값
|  데모 쇼핑몰에 오신 것을     |
|  환영해요. 무엇을 도와       |
|  드릴까요?                   |
|                              |
|  [ 공지사항 ] [ 배송 조회 ]  |   <- 바로가기 버튼 (최대 3개)
|------------------------------|
| 메시지를 입력하세요   [보내기]|
+------------------------------+
```

- 인사말은 **대화 맨 위에 상담원 말풍선처럼** 보입니다. 보낸 사람은 조직 이름과 로고입니다.
- 운영 시간 밖이면 인사말 대신 **부재 인사말**을 보여줍니다(4-4).
- 바로가기 버튼은 `https://` 주소만 받고 새 탭으로 엽니다. 가이드 글을 고르면 공개 가이드 주소(`guide_model.public_url()`)를 넣습니다.

### 2-2. 언제 저장하는가

`init` 마다 인사말을 메시지로 저장하면 위젯을 열기만 한 방문자 수만큼 메시지가 쌓입니다.

- **화면에만 그리고 저장하지 않습니다.** `init` 응답에 인사말을 담아 위젯이 그립니다.
- 방문자가 **첫 메시지를 보낼 때**, 그 앞에 인사말을 `sender_type='system'`, `meta.type='greeting'` 으로 한 번 저장합니다.
  상담원 콘솔에서도 고객이 어떤 안내를 보고 말을 걸었는지 보입니다.
- 저장할 때 발행도 합니다(3.11).

### 2-3. 다국어 인사말

```
인사말 탭
-----------------------------------------------------------
 기본 (한국어)                                    조직 언어
 +-------------------------------------------------------+
 | {{이름|고객}}님 안녕하세요!                            |
 | {{조직}}에 오신 것을 환영해요. 무엇을 도와드릴까요?   |
 +-------------------------------------------------------+
 [변수 넣기 v]  [버튼 추가]

 English                                             [삭제]
 +-------------------------------------------------------+
 | Hello {{name|there}}! ...                             |
 +-------------------------------------------------------+

 [+ 언어 추가]  -> 검색 가능한 언어 목록
-----------------------------------------------------------
 [x] 고객 브라우저 언어에 맞춰 보여주기
```

- **기본 인사말은 조직 언어로 하나 반드시** 있습니다. 다른 언어는 추가로 넣습니다.
- 추가할 수 있는 언어는 **인사말 문구용 목록**으로, UI 사전(ko/en/ja)보다 넓습니다(약 30개, 허용 목록 검사).
  인사말은 조직이 직접 쓰는 글이라 사전이 필요 없기 때문입니다.
- 고르는 순서: 브라우저 `navigator.languages` 를 앞에서부터 보며 **언어 코드 앞부분**(`en-US` → `en`)이 맞는 인사말 → 기본 인사말.
- 같은 규칙으로 **위젯 UI 문구 언어**도 정합니다. 단, UI 사전은 ko/en/ja 뿐이므로 그 밖의 언어는 조직 언어로 그립니다.
  예: 스페인어 인사말 + 한국어 버튼 문구가 함께 나올 수 있습니다. 9장 1번에서 결정이 필요합니다.
- 브라우저 언어 따르기를 끄면 지금처럼 조직 언어 하나만 씁니다(기본값: 끔). 지금 쓰는 조직의 동작이 바뀌지 않게 하려는 것입니다.
- 서버가 판단하지 않고 위젯이 고르게 하려면 `init` 이 모든 언어 인사말을 내려야 합니다. 대신 위젯이 `init` 요청에
  `languages: navigator.languages` 를 실어 보내고 **서버가 하나만 골라** 내려줍니다. 응답 크기가 줄고 고르는 규칙이 한 곳에 있습니다.

### 2-4. 개인화 변수

| 변수 | 값 | 비어 있을 때 |
|---|---|---|
| `{{이름}}` / `{{name}}` | `visitors.name` | `|` 뒤 기본값, 없으면 빈 문자열 |
| `{{조직}}` / `{{org}}` | 조직 이름 | — |

- 문법: `{{이름|고객}}` — 이름이 없으면 "고객". 편집기에서는 [변수 넣기] 로만 넣고 칩 모양으로 보여줍니다(2단계, 1단계는 글자 그대로).
- **치환은 서버가 하고 결과는 글자로 내려보냅니다.** 위젯은 HTML 로 넣지 않고 `textContent` 로 그립니다.
  방문자가 이름에 태그를 넣어도 그대로 글자로 보입니다.
- 모르는 변수는 그대로 둡니다. 저장할 때 모르는 변수가 있으면 경고만 하고 막지는 않습니다.
- 변수는 이 둘로 시작하고, 고객사가 스니펫에 사용자 정보를 넘기는 기능(`data-name` 등)이 생기면 늘립니다.

### 2-5. 데이터

```sql
widget_greetings
  id, org_id,
  kind     ENUM('greeting','away')   -- 인사말 / 부재 인사말
  lang     VARCHAR(10)               -- 'ko', 'en', 'es', ... (허용 목록)
  body     TEXT                      -- 1,000자 이내, HTML 받지 않음
  buttons  JSON                      -- [{label, url}] 최대 3개, url 은 https 만
  updated_at
  UNIQUE (org_id, kind, lang)

organizations
  + widget_follow_browser_lang TINYINT(1) NOT NULL DEFAULT 0
```

인사말이 하나도 없는 조직은 지금 문구(`widget.title`, `widget.subtitle`)를 그대로 씁니다.

## 3. 팔로업 알림

### 3-1. 무엇을 하는가

고객이 문의를 남기고 사이트를 떠나면 상담원의 답을 볼 수 없습니다.
연락처를 받아 두었다가, **고객이 위젯을 보고 있지 않을 때 상담원이 답하면** 그 연락처로 알립니다.
알림에는 대화를 이어 갈 수 있는 링크가 들어 있습니다.

### 3-2. 설정

```
팔로업 탭
-----------------------------------------------------------
 받을 연락처
   이메일    [켜짐]   상담원 답장을 이메일로 알립니다
   휴대폰    [꺼짐]   문자 발송 수단이 준비되면 켤 수 있습니다   (비활성)
   이름      [꺼짐]   알림에는 쓰지 않고 상담원이 볼 수 있게 저장합니다

 [ ] 연락처를 남긴 고객에게만 문의받기
     연락처를 입력해야 상담이 시작됩니다. 입력하지 않고 떠난 고객의 문의는 상담 대화에 들어오지 않습니다.

 수집 안내 문구 (언어별, 인사말과 같은 방식)
 +-------------------------------------------------------+
 | 답변 알림을 받을 연락처를 남겨 주세요. 입력하신 정보는 |
 | 이 문의에 답변하는 데에만 사용합니다.                  |
 +-------------------------------------------------------+
-----------------------------------------------------------
  ! 수집한 연락처는 고객이 요청한 상담에 답하는 목적으로만 씁니다.
    다른 목적에 쓰려면 고객에게 따로 동의를 받아야 합니다.
```

- **휴대폰 알림은 발송 수단이 정해질 때까지 비활성**입니다(9장 2번). 휴대폰 칸을 켜면 번호를 저장만 하고 알림은 보내지 않습니다.
  저장만 하더라도 상담원이 전화로 연락할 수 있으므로 의미가 있습니다.
- 휴대폰과 이메일을 모두 켜고 둘 다 받으면 둘 다로 보냅니다.

### 3-3. 고객이 보는 화면 — 연락처 카드

위쪽에 늘 떠 있던 이름/이메일 칸은 없애고, **대화 안에 카드로** 묻습니다.

```
 [고객] 주문한 상품이 아직 안 왔어요
 [시스템 카드]
 +--------------------------------------+
 | 자리를 비우셔도 답변을 알려 드려요.  |
 | 휴대폰  [+82 v][010-0000-0000   ]    |
 | 이메일  [                       ]    |
 | 개인정보 수집 안내 문구               |
 |                         [ 제출 ]     |
 +--------------------------------------+
```

| 설정 | 카드가 나오는 때 | 카드를 내기 전 메시지 |
|---|---|---|
| 일반 | 고객의 **첫 메시지 직후**, 연락처가 아직 없을 때 한 번 | 그대로 전송되고 상담원에게 보인다 |
| 연락처 있는 고객에게만 | 위젯을 열자마자. 입력창은 연락처를 내기 전까지 잠긴다 | 보낼 수 없다 |

- 카드를 닫거나 건너뛰면 그 대화에서 다시 묻지 않습니다. 상담원이 콘솔에서 [연락처 요청] 으로 다시 띄울 수 있습니다.
- 이미 받은 연락처가 있으면(같은 `visitor_key`) 묻지 않고, 위젯 메뉴에서 고칠 수 있게 합니다.
- "연락처 있는 고객에게만" 일 때, **대화는 연락처를 받은 뒤에 만듭니다.** 지금은 `init` 이 빈 대화를 만들어 두므로,
  이 설정에서는 빈 대화를 콘솔 목록에 보이지 않게 거릅니다(`last_message_at IS NULL` 숨김, 다른 설정에도 함께 적용).

**입력 검사(서버)**

| 항목 | 규칙 |
|---|---|
| 이메일 | `valid_email()`(helpers/validation.py), 190자 |
| 휴대폰 | 국가번호 허용 목록(`supported_countries()` 기준) + 숫자만, E.164(`+821012345678`)로 저장 |
| 이름 | 60자, 앞뒤 공백 제거 |
| 동의 | 수집 안내를 보여 준 상태에서 제출했을 때 `contact_consent_at` 기록 |

### 3-4. 언제 알리는가 — 예약 작업 없이

이 저장소에는 cron 이 없습니다. 새로 만들지 않고 **상담원이 메시지를 보낼 때 바로 판단**합니다.

```
상담원 답장 저장 (console.api_chat_send)
  -> realtime 발행 (지금도 함)
  -> 팔로업 판단
       1. 이 대화의 고객 연락처가 있는가
       2. 고객이 지금 위젯을 보고 있지 않은가
       3. 이 대화에 최근 10분 안에 보낸 알림이 없는가
     -> 모두 맞으면 이메일 발송, followup_notices 에 기록
```

**"고객이 보고 있지 않다" 판단**

- 1순위: realtime-msg 의 `conv:{id}` 구독자 수. `/publish` 응답에 그 방의 구독자 수를 담도록 `realtime/` 을 고칩니다.
  0 이면 위젯 창이 닫혔거나 페이지를 떠난 것입니다.
- 2순위(realtime 이 꺼져 있거나 응답이 없을 때): `visitors.last_seen_at` 이 90초보다 오래됐으면 떠난 것으로 봅니다.
  위젯 폴링이 실시간 연결 중에는 30초라 그보다 넉넉히 잡습니다.
- 위젯이 페이지에 있지만 **창이 접혀 있으면** 구독은 살아 있어도 고객은 못 봅니다. 위젯이 접기/펴기를 서버에 알리지 않고,
  구독 시 `visible` 여부를 함께 보내 realtime-msg 가 "펼쳐진 구독자 수" 를 세게 합니다(2단계).

**몰아서 보내기**

- 같은 대화에는 **10분에 한 번**만 보냅니다. 그 사이 상담원이 여러 번 답해도 메일은 한 통입니다.
- 메일에는 "새 답변이 n개 있습니다" 와 마지막 답장 앞부분(200자)만 넣고, 나머지는 링크에서 봅니다.
- 고객이 대화를 다시 열면(`init`/`poll`) 10분 제한을 풀어, 다음에 떠났을 때 바로 알릴 수 있게 합니다.

### 3-5. 대화로 돌아오는 링크

고객이 다른 기기(휴대폰 메일 앱)에서 링크를 열 수도 있으므로, 원래 사이트로 보내지 않고
**포털의 고객 화면에서 대화를 이어 갑니다.**

```
{customer_url(org_code)}/chat/{resume_token}
  -> layouts/customer.html 에 위젯을 펼친 상태로 띄운다
  -> resume_token 을 검증해 그 대화의 visitor_key 로 위젯을 시작
```

- 주소는 `customer_url()` 로 만듭니다(3.13). 상담원이 localhost 로 콘솔을 열었더라도 고객에게는 공개 주소가 갑니다.
- `resume_token` 은 `conversation_id` + 만료 시각을 HMAC 서명한 값입니다(키는 `.env` 의 새 값 `CHAT_RESUME_SECRET`).
  만료는 14일. 대화가 닫혔으면 "종료된 상담입니다" 와 새 문의 버튼을 보여줍니다.
- 링크를 열면 그 브라우저에 `visitor_key` 를 새로 저장합니다. 같은 사람의 기기가 늘어나는 것이므로
  `visitor_key` 자체를 메일에 넣지 않고 토큰으로만 바꿔 줍니다.
- 경로는 `/{org_code}/chat/{token}`(routers/customer.py)이며 조직 코드 라우터보다 먼저 등록합니다(3.8).

## 4. 운영 시간

### 4-1. 개념

| 용어 | 뜻 |
|---|---|
| 운영 설정 | 이름 + 시간대 + 요일별 운영 시간 + 휴일. 조직마다 **기본 운영 설정 1개**가 항상 있다 |
| 담당 상담원 | 운영 설정에 속한 상담원. 기본 운영 설정은 다른 설정에 속하지 않은 모든 상담원 |
| 운영 중 | 지금 시각이 그 설정의 운영 시간 안이고 휴일이 아님 |

- 조직당 최대 20개입니다(참고한 서비스는 50개지만 우리 요금제는 상담원 5명 기준입니다. 늘리기는 쉽습니다).
- 팀 기능이 따로 없으므로 **운영 설정이 곧 팀(창구) 역할**을 합니다. 예: 한국 오피스, 일본 오피스, 기술 지원.

### 4-2. 설정 화면

```
운영 시간 탭                                   [+ 운영 설정 추가]
-----------------------------------------------------------------
  [깃발] 기본 운영        운영 중     Asia/Seoul (UTC+09:00)   상담원 3명  >
         일본 오피스      운영 중     Asia/Tokyo (UTC+09:00)   상담원 1명  >
         Sales-뉴욕       운영 전     America/New_York (-04:00) 상담원 1명  >
-----------------------------------------------------------------

편집 모달 (openModal)
  이름        [일본 오피스        ]
  시간대      [Asia/Tokyo       v]   (허용 목록)
  운영 시간
    월 [x] 09:00 ~ 18:00  [+ 구간]
    화 [x] 09:00 ~ 12:00, 13:00 ~ 18:00
    ...
    토 [ ] 휴무
    일 [ ] 휴무
    [ ] 24시간 운영
  휴일        [2026-12-25 성탄절] [+ 날짜]
  담당 상담원 [x] 김상담 [ ] 이상담 ...      (기본 운영 설정에는 없음)
  운영 시간 밖에 [ ] 문의 받지 않기
                                                 [삭제] [저장]
```

- 하루에 구간을 여러 개 둘 수 있습니다(점심시간 제외). 자정을 넘는 구간(22:00~02:00)은 저장할 때 두 요일로 나눕니다.
- 기본 운영 설정은 지울 수 없고 이름만 바꿀 수 있습니다.
- 처음 탭을 열 때 기본 운영 설정이 없으면 **24시간 운영**으로 만듭니다. 지금 쓰는 조직의 동작이 바뀌지 않습니다.
- 공휴일 일괄 불러오기는 1단계에서 빼고 날짜를 직접 넣습니다.

### 4-3. 시각 규칙 — UTC 저장의 예외

운영 시간은 **시각이 아니라 벽시계 규칙**("월요일 09:00, 도쿄 기준")입니다. UTC 로 바꿔 저장하면
서머타임이 있는 시간대에서 1년에 두 번 한 시간씩 밀립니다.

- 운영 시간과 휴일은 **설정의 시간대 기준 현지 시각(분 단위 정수)과 날짜**로 저장합니다.
- 판단은 지금 시각을 설정 시간대(`ZoneInfo`)로 바꿔 현지 요일·분을 구해 비교합니다(`chat_hours_model.availability()`).
- 화면에 "다음 운영: 월 09:00" 을 보여줄 때는 다음 시작 시각을 **UTC 로 계산해 내려보내고** 위젯이 고객 시간대로 그립니다(3.4).
- 이 예외를 CLAUDE.md 3.4 에 한 줄 추가합니다. 검사 스크립트가 시간 컬럼을 보는 규칙이 있다면 예외 목록에 넣습니다.

### 4-4. 위젯 동작

**운영 설정이 1개일 때**

| 상태 | 머리글 | 대화창 |
|---|---|---|
| 운영 중 + 상담원 접속 | ● 운영 중 · 보통 몇 분 안에 답해요 | 인사말 |
| 운영 중 + 접속자 없음 | ● 운영 중 · 곧 답해 드려요 | 인사말 |
| 운영 시간 밖 | ○ 운영 시간이 아닙니다 · 월 09:00 부터 | **부재 인사말** + 연락처 카드를 바로 띄움 |
| 운영 시간 밖 + 문의 받지 않기 | 위와 같음 | 입력창 잠김, 운영 시간 안내만 |

**운영 설정이 2개 이상일 때**

첫 메시지를 보내기 전에 창구를 고르게 합니다.

```
 어느 창구에 문의하시겠어요?
 +-------------------------------------+
 | 기본 운영            ● 운영 중       |
 | 일본 오피스          ● 운영 중       |
 | Sales-뉴욕           ○ 22:00 부터    |
 +-------------------------------------+
```

- 고른 창구는 `conversations.schedule_id` 에 저장하고, 상태 표시와 부재 인사말은 그 창구 기준입니다.
- 창구 목록에서 이름만 보이고 내부 정보(상담원 이름 등)는 내려보내지 않습니다.
- 운영 시간 밖 창구도 고를 수 있습니다(문의 받지 않기 설정이면 고를 수 없음).

### 4-5. 상담원 콘솔과 알림

- 대화 목록에 창구 열과 필터를 추가합니다. 상담원은 **자기 창구 대화가 위로** 오지만 다른 창구 대화도 볼 수 있습니다
  (권한으로 막지 않습니다. 작은 조직에서 서로 도와야 하므로).
- 운영 시간 밖에 들어온 대화에는 `운영 시간 외` 배지를 붙입니다(`conversations.received_off_hours`).
- 지금의 조직 오프라인 메일(`notify_if_offline`)은 "운영 중인데 접속자가 없을 때" 만 보냅니다.
  운영 시간 밖 문의는 다음 운영 시작에 콘솔에서 확인하는 흐름이라 메일을 매번 보내지 않습니다.
  (예약 작업이 없으므로 "다음 운영 시작 시 요약 메일" 은 하지 않습니다.)

## 5. 위젯 API 변경

| API | 바뀌는 것 |
|---|---|
| `POST /api/widget/init` | 요청에 `languages`. 응답에 `greeting{body, buttons}`, `schedules[{id,name,open,next_open_utc}]`, `followup{fields, required, notice}`, `lang` |
| `POST /api/widget/send` | `schedule_id`(창구가 2개 이상일 때 필수, 그 조직 것인지 검사). 첫 메시지면 인사말 저장 |
| `POST /api/widget/contact` (신규) | 연락처 제출. 입력 검사 후 `visitors` 갱신, 동의 시각 기록 |
| `GET /{org_code}/chat/{token}` (신규) | 팔로업 링크로 대화 이어가기 |

- 위젯은 계속 **의존성 없이** 돌고(3.9), 새 화면(인사말 버튼, 연락처 카드, 창구 선택)도 Shadow DOM 안에 그립니다.
- 위젯 고정 문구는 지금처럼 `widget_texts()` 로 내려줍니다. 새 키는 ko/en/ja 세 사전에 함께 넣습니다(3.2).
- 이름/이메일을 `send` 에 함께 보내던 방식은 `contact` 로 옮기고, 구버전 위젯 캐시를 위해 `send` 쪽 처리는 한동안 남깁니다.

## 7. 작업 순서

인사말의 부재 문구는 운영 시간이 있어야 의미가 있고, 팔로업은 연락처 카드가 있어야 하므로 아래 순서로 갑니다.

| 단계 | 내용 | 비고 |
|---|---|---|
| 1 | 드로어 탭 구조로 개편 (기존 항목은 "설치·모양" 탭으로) | 화면만 |
| 2 | 인사말 — 조직 언어 하나 + `{{이름}}`/`{{조직}}` + 바로가기 버튼, 첫 메시지 때 저장 | |
| 3 | 운영 시간 — 기본 운영 설정 1개, 요일·구간·휴일, 부재 인사말, 위젯 상태 표시 | |
| 4 | 연락처 카드 — 이메일/휴대폰/이름, 필수 모드, 위쪽 입력칸 제거 | |
| 5 | 팔로업 이메일 — realtime 구독자 수, 10분 묶음, 이어가기 링크 | `realtime/` 수정 |
| 6 | 다국어 인사말 + 브라우저 언어 따르기 | 9장 1번 결정 후 |
| 7 | 여러 운영 설정 + 창구 선택 + 콘솔 필터 | |
| 8 | 문자/알림톡 팔로업 | 9장 2번 결정 후 |

단계마다 `./scripts/check-conventions.sh` 를 통과시키고, 5단계는 realtime 을 건드리므로 `e2e-test.sh` 도 돌립니다.
마이그레이션은 `sql/migrations/009-widget-ops.sql` 부터 단계별로 나누고 `sql/01-schema.sql` 에도 반영합니다.

**검사 스크립트에 넣을 것**(CLAUDE.md 7장)

- `widget_texts()` 키가 세 사전에 모두 있는지 (지금 일반 사전 검사로 잡히는지 먼저 확인)
- 상담원 메시지를 저장하는 곳에서 팔로업 판단을 부르는지 (발행 누락 검사와 같은 방식)

## 8. 하지 않는 것

- 운영 시간 밖 문의를 다음 운영 시작에 몰아서 알리는 메일 — 예약 작업이 없어서
- 공휴일 자동 불러오기 — 나라별 데이터 관리가 필요
- 상담원별 개인 근무 시간 — 운영 설정 단위로만 관리
- 인사말 자동 번역 — 참고 서비스의 [번역] 버튼. 외부 번역 API 비용과 키 관리가 필요해 뺐습니다
- 고객사 스니펫으로 회원 정보 넘기기(`data-name` 등) — 변수 확장과 함께 따로 기획

## 9. 확인이 필요한 사항

1. **위젯 언어 규칙 변경** — 지금 CLAUDE.md 3.2 는 "고객 화면은 조직 설정 언어" 입니다. 브라우저 언어를 따르는 선택 사항을 두려면
   규칙을 "조직 설정, 단 조직이 브라우저 언어 따르기를 켜면 브라우저 언어(ko/en/ja 안에서)" 로 바꿔야 합니다.
   ko/en/ja 밖의 언어 방문자에게 **인사말은 그 언어, 버튼 문구는 조직 언어**로 섞여 나오는 것을 받아들일지도 정해야 합니다.
2. **휴대폰 알림 수단** — 문자/알림톡 발송 업체와 비용, 알림톡이면 카카오 비즈니스 채널과 템플릿 심사가 필요합니다.
   참고 서비스처럼 "결제 수단 등록 조직만" 으로 제한할지, 요금(`routers/home.py` 의 `pricing`)에 포함할지도 정해야 합니다.
3. **연락처 보관 기간** — 대화가 끝난 뒤 이메일·휴대폰을 언제 지울지. 개인정보처리방침에 적을 내용입니다.
4. **SMTP** — 팔로업은 고객에게 가는 메일이라 발송량이 조직 오프라인 알림보다 훨씬 많습니다.
   시험 서버 SMTP 설정 상태와, 발송 도메인의 SPF/DKIM 설정이 되어 있는지 확인이 필요합니다(안 되어 있으면 스팸함으로 갑니다).
5. **운영 설정 상한** — 20개로 두었습니다. 요금제와 연결할지.
6. **"연락처 있는 고객에게만" 의 기존 대화** — 이 설정을 켜기 전에 열린 대화는 그대로 두는 것으로 잡았습니다.

### 10-2. 확인한 것

- 설정 저장 검사: http/`javascript:` 버튼 주소, 버튼 4개, 필수인데 항목 없음은 400. 모르는 변수는 저장하고 경고.
- 위젯: 대화 전에는 인사말을 화면에만, 첫 메시지 때 인사말 → 고객 글 → 자동 응답 순서로 저장·발행, 두 번째 메시지부터는 저장하지 않음.
- 연락처: 잘못된 이메일·번호·허용 밖 국가 거부, 묻지 않는 항목 버림, 필수 모드에서 연락처 없이 보내기·건너뛰기 409.
- 팔로업 판단(메일러만 가짜로 바꿔 시험): 보고 있으면 안 보냄 / 떠났으면 보냄 / 바로 다시 답하면 안 보냄 / 다시 와서 보고 떠나면 다시 보냄. 긴 답장은 200자로 자름.
- 이어 가기: 맞는 토큰은 원래 방문자와 대화로 이어지고, 서명이나 본문을 바꾼 토큰은 새 방문자로 시작.
- 화면: 위젯(필수 모드 카드, 기본 모드 카드, 저장 후 순서)과 설정 드로어 두 탭을 브라우저로 찍어 확인.

**확인하지 못한 것**: 실제 SMTP 발송(개발 환경에 메일 서버 없음), 실제 메일 앱에서 주소를 눌러 다른 기기로 이어 가기.
